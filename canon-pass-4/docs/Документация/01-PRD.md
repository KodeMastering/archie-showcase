## 1. Executive Summary

Archie — проактивный ИИ-напарник, интегрированный на уровень операционной системы и работающий на любом, в том числе слабом, «студенческом» железе без дискретной видеокарты. В отличие от реактивных ассистентов (Siri, базовый Copilot, Алиса) Archie сам замечает, что пользователь застрял, устал или выполняет рутину, и предлагает помощь до явного запроса. В отличие от open-source локальных агентов класса Jarvis, Archie не требует 16–24 ГБ VRAM: тяжёлая логика делегируется в облако (DeepSeek / OpenAI / Gemini), а локальный edge-контур (Tauri v2 + Rust + Python) отвечает за сенсорику, приватность и миллисекундную отзывчивость.

**Роадмап из четырёх фаз:**

| Фаза | Версия | Суть | Ключевой SLA-контракт |
|---|---|---|---|
| 1 | MVP Alpha | Ядро (Event Bus), Z-Sense, полнодуплексный голос с Barge-in, офлайн-фолбэк | Barge-in < 200 мс; OCR ~200 мс; RAM Idle 150 МБ |
| 2 | B2C Beta | Проактивность (Frustration Index, Mission States), трёхуровневая память, Permission Tiers, Staging-зоны, онбординг Path A/B | Порог фрустрации 50; окно отмены 3–5 с; RAM Peak 655 МБ |
| 3 | v1.0 Production | Semantic Router, SOP Blueprints, автообновление, мультиплатформенность | Совпадение SOP-триггера >= 0.98 |
| 4 | v2.0 Enterprise | B2B-pivot: Jira/Slack MCP, Junior Mentor, Burnout Tracker, On-Premise | RAM Offline 1450 МБ; 100% PII-маскирование |

**B2C → B2B тезис:** MVP строится для B2C-сегментов (студенты/ЕГЭ, начинающие разработчики, геймеры), но архитектура с первого дня закладывает enterprise-контуры (PII Sanitizer, MCP-хаб, audit log, заменяемый облачный шлюз), чтобы pivot в корпоративный сегмент не требовал перестройки.

**Headline-SLA (канон RFC-0001, см. раздел 6):** Barge-in < 200 мс; VAD-детекция 85–100 мс (точность > 95%); OCR ~200 мс (эталон 185 мс); RAM 150 / 655 / 1450 МБ (Idle / Peak / Offline); порог фрустрации 50 (S_max = 100, полураспад 20/15/5/1 мин по миссиям); совпадение SOP >= 0.98; инсталлятор ~8 МБ без весов моделей.

## 2. Vision, Goals и Non-Goals

### 2.1 Vision

Первый по-настоящему живой, полезный и безопасный ОС-напарник: общение в модели «Старший брат / Ментор» (Big Brother Persona), живые интонации, мгновенное перебивание, проактивная помощь без спама и детерминированная безопасность автономных действий.

### 2.2 Дифференциация

1. **Проактивность + эмпатия** — индекс фрустрации и машина состояний миссии (GAMING_REST / STUDY_FOCUS / CODING_WORK / IDLE) вместо принципа «вопрос–ответ».
2. **Слабое железо** — гибрид edge+cloud: локальный клиент лёгок (инсталлятор ~8 МБ, RAM Idle 150 МБ), тяжёлый инференс в облаке, офлайн-фолбэк на локальную SLM 1.5B.
3. **Безопасная автономность** — Permission Tiers, карантинная Staging-зона (физический запрет Delete), SOP Blueprints, превращающие вероятностные догадки LLM в детерминированные скрипты при совпадении >= 0.98.
4. **Приватность local-first** — сырые кадры экрана и аудио не покидают устройство; в облако уходит только санированный текстовый слепок (после PII Sanitizer).

### 2.3 Goals (по фазам)

- **MVP Alpha:** доказать жизнеспособность гибридного ядра и голосового тракта: живой диалог с перебиванием < 200 мс на целевом слабом железе, внутренний dogfood.
- **B2C Beta:** проактивный напарник для 100–500 внешних пользователей; измерить activation и proactivity acceptance.
- **v1.0 Production:** публичный запуск, самопрограммирование (SOP), auto-update, мультиплатформенность (Windows / macOS / Linux).
- **v2.0 Enterprise:** корпоративный пилот (Junior Mentor, Jira/Slack, Burnout Tracker, On-Premise).

### 2.4 Non-Goals (что мы НЕ строим — глобально)

- НЕ строим записывающий «видео-дневник» экрана (антипаттерн Rewind.ai): сырые кадры и аудио не хранятся и не передаются.
- НЕ строим полностью локальный тяжёлый LLM-стек: требование дискретной GPU противоречит целевому железу.
- НЕ строим мобильную/смарт-спикерную версию в горизонте фаз 1–3.
- НЕ строим тонкую настройку (fine-tune) проприетарных облачных моделей.
- НЕ позиционируем Archie как инструмент слежки: Burnout Tracker (v2.0) — только анонимизированные агрегаты, с прозрачностью для сотрудника.

## 3. Персоны и сценарии

Персоны привязаны к mission states, чтобы UX-спека и GTM-документ наследовали единый словарь «персона → состояние».

### P1. Студент / ЕГЭ («Миша, 17»)
- **Контекст:** ноутбук 8 ГБ RAM без GPU, подготовка к ЕГЭ + изучение Python; слабая самодисциплина, прокрастинация.
- **Цели:** сосредоточиться на заданиях, не залипнуть в соцсетях; понять, где ошибся в разборе задачи.
- **Фрустрации:** ассистенты «не в контексте»; репетитор дорог; сервисы жрут память ноутбука.
- **Сигнатурный сценарий (STUDY_FOCUS):** Миша 15 минут сидит на одной вкладке без скролла, потом тяжело вздыхает — счётчик фрустрации превышает 50, Soft Widget мягко предлагает разбор задачи; при открытии Steam миссия = GAMING_REST и Archie молчит.
- **Цитата:** «Хочу, чтобы кто-то заметил, что я залип, и вернул меня в работу — но не читал нотации, когда я отдыхаю».

### P2. Начинающий разработчик («Настя, 21»)
- **Контекст:** ноутбук 8–16 ГБ, VS Code, Python, репозитории на GitHub; страх «сломать что-то» в терминале.
- **Цели:** быстрая помощь по ошибке в коде в контексте её проекта; автоматизировать рутину (коммит + дневник) без риска.
- **Фрустрации:** копировать ошибку в чат-бот — теряется контекст; автоматизация пугает («а вдруг удалит»).
- **Сигнатурный сценарий (CODING_WORK):** `IndentationError` 4 раза подряд (+20 баллов) + цикл переписывания блока кода (+15) — Archie указывает на отступ; после закрытия VS Code предлагает Blueprint: «делать Git Commit + запись в Obsidian?» (Tier 2 подтверждение, окно отмены 3–5 с).
- **Цитата:** «Пусть готовит коммит, но пушит только после моего "да"».

### P3. Геймер («Дима, 24»)
- **Контекст:** Windows, полноэкранные игры, фоновая музыка; не терпит лагов и всплывающих окон поверх игры.
- **Цели:** напомнить про перерыв/отдых, не вмешиваясь в процесс; не проседал FPS.
- **Фрустрации:** оверлеи, которые ломают fullscreen; ассистент, который «умничает» во время катки.
- **Сигнатурный сценарий (GAMING_REST):** проактивность принудительно 0%; виджет обязан рендериться поверх полноэкранной игры, не перехватывая ввод (dual-window Tauri-архитектура, Show Desktop immunity); перерыв предлагается только в паузах меню, голосовое вмешательство — только по прямому обращению.
- **Цитата:** «Ты нужен, только когда я сам тебя позову, или между матчами».

### P4. Junior в Enterprise (B2B, v2.0) («Игорь, 23, стажёр финтеха»)
- **Контекст:** рабочая машина в корпоративном периметре, Jira/Slack/Confluence, строгие политики ИБ.
- **Цели:** не отвлекать Senior: как поднять базу, где взять ключи, какой скрипт запустить.
- **Фрустрации:** «спрашивать стыдно, гуглить долго».
- **Сигнатурный сценарий:** Archie по экрану стажёра подсказывает следующий шаг; утверждённые регламенты компании (SOP через MCP: Jira, Slack, git) выполняются детерминированно; Burnout Tracker отдаёт HR только анонимные тепловые карты; данные не покидают периметр (On-Premise).
- **Цитата:** «Хочу наставника, который видит мой экран, но не пишет на меня докладные».

## 4. Scope по фазам (MoSCoW) и pivot-триггеры

Приоритеты MoSCoW применяются **внутри каждой фазы**. Каждая фаза имеет измеримые exit-критерии (раздел 9) и явный список «не строим в этой фазе».

### 4.1 Фаза 1 — MVP Alpha

- **Must:** Event Bus (Rust/tokio) с контрактом событий; двухоконная оболочка Tauri v2 (soft widget + скрытый main_dashboard, prevent_close()+hide(), tray, single-instance, HiDPI); Z-Sense (OS-триггеры, Accessibility API, RapidOCR ~200 мс, XY-cut сортировка, JSON-граф); аудио-цикл single-process (AEC3, Silero VAD, Sherpa-ONNX, Piper TTS) с Barge-in < 200 мс; cloud gateway (DeepSeek/OpenAI/Gemini) + graceful degradation на локальную SLM 1.5B (API_TIMEOUT); системный промпт Big Brother; Path A onboarding; Tier 0/1 permissions; RAM Idle 150 МБ.
- **Should:** детекция тяжёлых вздохов (sigh detector); базовые глобальные хоткеи с детектором конфликтов.
- **Could:** префильтр Apple Vision на macOS.
- **Won't (в этой фазе):** Tier 2 approval cards; semantic router; память уровня 2/3; telemetry; мультиплатформенность (одна платформа); Path B.

### 4.2 Фаза 2 — B2C Beta

- **Must:** Mission-State Machine; Frustration Index (порог 50, decay 20/15/5/1 мин); Soft Widget с окном отмены 3–5 с; внутренний монолог (скрытый облачный запрос); tri-level memory (RAM-сессия 2–4 ч, ночные сводки → MCP Obsidian/Notion, VectorDB RAG); PII Sanitizer v1 (regex + NER) перед облаком; Staging-зоны и Tier 2 Critical Approval; Path B (тихое наблюдение); opt-in telemetry; RAM Peak 655 МБ.
- **Should:** первый MCP reference server (obsidian_vault); SOP-черновики как концепт (без автозапуска); анти-ложные срабатывания фрустрации при видеолекциях (заморозка таймера стагнации при активном медиапотоке).
- **Could:** Baseline-библиотека из 5–10 курируемых SOP.
- **Won't:** автоисполнение SOP (semantic router); Tier 3 Context Workspaces; auto-update; Linux-сборка; enterprise-функции.

### 4.3 Фаза 3 — v1.0 Production

- **Must:** Semantic Router (совпадение >= 0.98 → обход облачной LLM, детерминированный скрипт); SOP sandbox/AST-валидация (MCP-only tool calls, карантин Staging); Tier 3 Context Workspaces («Я хочу учиться»); auto-update + отдельная дистрибуция model artifacts (ONNX/GGUF, версионируемые, не в инсталляторе ~8 МБ); мультиплатформенность; WCAG 2.2 AA для UI-поверхностей; RAM Offline 1450 МБ.
- **Should:** полная SOP-библиотека; менеджер рецептов (BlueprintManager); детектор конфликтов шорткатов.
- **Could:** import/export профиля памяти.
- **Won't:** SSO/admin console; on-prem; Burnout Tracker (архитектурные закладки — да, фичи — нет).

### 4.4 Фаза 4 — v2.0 Enterprise

- **Must:** enterprise_jira_slack MCP-серверы; SSO/admin console/централизованные политики; tamper-evident audit log; On-Premise/VPC-вариант; Junior Mentor; Burnout Tracker (анонимные агрегаты); SOC 2 путь для облачных компонентов.
- **Should:** ISO 27001 (stretch); data residency options (EU/US/on-prem).
- **Could:** RBAC-гранулярность политик по департаментам.

### 4.5 B2B pivot-триггеры

Определяются **до** pivot, пересматриваются ежемесячно владельцем = founder по телеметрии Beta (формулировки идентичны GTM-документу — единый словарь метрик):

| Триггер | Порог (placeholder, [uncertain]) | Действие |
|---|---|---|
| B2C paid conversion < X% через 6 мес после v1.0 | X — не задан командой | Перебалансировка roadmap в сторону Enterprise-фич |
| Inbound B2B demand >= Y квалифицированных запросов | Y — не задан | Досрочный старт enterprise-track |
| Cloud API cost / active user вне маржи Business Model | по числам финплана | Приоритет cost-оптимизации (роутер, локальные модели) |

**Правило scope-контроля:** новая FR должна вытеснить FR равного приоритета или ждать следующей фазы. Любая «демо-исключка» — только за feature flag с тикетом на удаление до exit следующей фазы.

## 5. Functional Requirements (FR)

Формат таблицы: ID | Требование | Модуль (монорепо) | Фаза | MoSCoW | Source | Критерий приёмки (Given/When/Then — выборка ключевых). Каждая FR трассируется минимум на одну персону/user story. Полные Gherkin-сценарии — в `07-Testing-QA-Strategy.md`.

### FR-ZS — Z-Sense (сенсорика экрана)

- **FR-001** (Z-Sense, Ф1, Must, PAD §3.1 / RFC-0001): Система ДОЛЖНА собирать экранный контекст только по событиям ОС (смена окна/вкладки, выделение текста, системная ошибка), без периодических полных скриншотов. *AC:* When пользователь меняет активное окно, Then генерируется событие `ZSENSE_GRAPH_READY` с JSON-графом, и средний сетевой трафик контекста за час dogfood-сессии снижен на ~99% относительно 5-секундных скриншотов.
- **FR-002** (Z-Sense, Ф1, Must, RFC-0001): OCR-конвейер (Accessibility API → RapidOCR ONNX, XY-cut сортировка) ДОЛЖЕН выдавать результат от захвата до текстового слепка за ~200 мс (эталон 185 мс) на целевом CPU. *AC:* p95 <= 250 мс на golden-наборе изображений, точность >= 95% на ground-truth тексте; hard fail выше 300 мс (CI-гейт). [uncertain: точный accuracy floor]
- **FR-003** (Z-Sense, Ф1, Must, PAD §3.1): Экранный контекст ДОЛЖЕН сериализоваться в компактный JSON-граф (`contracts/zsense_context.schema.json`), включающий `active_window`, `visible_text_snippet`, `error_state`, `mission_state`, `ocr_envelope` (координаты, confidence, elapsed_ms).

### FR-EB — Event Bus

- **FR-004** (archie-event-bus, Ф1, Must, ARCH §2): Все модули ДОЛЖНЫ взаимодействовать через типизированную шину событий (`contracts/events_envelope.schema.json`); замена одного движка (ASR/OCR) НЕ ДОЛЖНА требовать переписывания смежных модулей. *AC:* интеграционный тест подменяет OCR-модуль заглушкой — остальные подписчики работают без изменений контрактов.
- **FR-005** (archie-event-bus, Ф1, Must, ARCH §6): Падение любого одиночного воркера НЕ ДОЛЖНО ронять шину (изоляция процессов). *AC:* kill Python-воркера в CI — трей и оверлей живы, шина доставляет оставшиеся события.
- **FR-006** (Event Bus, Ф1, Must, RFC-0001): Событие `API_TIMEOUT` ДОЛЖНО активировать graceful degradation: переключение на локальную SLM 1.5B без потери голоса и локальных действий, с голосовым предупреждением «я пока без тяжёлых мозгов». *AC:* при отключении сети ответ на голосовой запрос возвращается от локальной модели < 5 с, локальные Tier 1 действия продолжают исполняться.
- **FR-007** (Event Bus, Ф1, Should, research «Late B2B pain»): Конверт событий ДОЛЖЕН нести forward-compat поля `actor`/`tenant` (зарезервированы для v2.0), чтобы Enterprise не требовал смены схемы.

### FR-AL — Аудио-цикл и Barge-in

- **FR-008** (audio_loop, Ф1, Must, RFC-0001 / ARCH §2.3): Аудио-контур (микрофон → AEC3 → VAD → STT → TTS-буфер) ОБЯЗАН исполняться в едином внутрипроцессном цикле с общим аудио-клоком. *AC:* кодовая ревью-гейт + тест double-talk: при одновременном воспроизведении и речи ассистент не самопрерывается (нет ложных FORCE_STOP_AUDIO от собственного голоса).
- **FR-009** (audio_loop, Ф1, Must, RFC-0001): Barge-in end-to-end ДОЛЖЕН завершаться < 200 мс от начала речи пользователя до остановки TTS и смены состояния. *AC:* p95 < 200 мс на audio-loopback-риге (виртуальное аудиоустройство в CI + аппаратный риг на приёмке); уровень сигнала/состояние изменяется наблюдаемо. Ложные срабатывания < 2% на 30-минутном гейминг-корпусе (цель, [uncertain] порог корпуса).
- **FR-010** (audio_loop, Ф1, Must, RFC-0001): VAD — детекция речи 85–100 мс, точность > 95% (Silero VAD, 30 мс чанки). *AC:* бенчмарк-гейт CI.
- **FR-011** (audio_loop, Ф1, Must, ARCH §2.3): Потоковый TTS ДОЛЖЕН начинать озвучку первого предложения до завершения LLM-генерации (буферизация до первого знака препинания).
- **FR-012** (audio_loop, Ф1, Should, PAD §8.2): Семантический классификатор Turn Detection ДОЛЖЕН отличать фоновые «угу» от команд «стоп, я понял» (endpointing ~400 мс / ~1400 мс).
- **FR-013** (audio_loop, Ф2, Should, GDPR/152-FZ): Аудиослушание — только wake-word с видимым индикатором; continuous-режим — opt-in; консент-флоу в онбординге; per-region policy gate перед запуском рынка.

### FR-FS — Frustration Scorer / проактивность

- **FR-014** (proactivity, Ф2, Must, PAD §5.2 / RFC-0001): Индекс фрустрации ДОЛЖЕН использовать эвристики: +10 (вкладка без скролла 15 мин), +15 (тройное переписывание блока кода), +20 (4 подряд Exception), +30 (тяжёлый вздох), с порогом 50, S_max = 100 и полураспадом 20/15/5/1 мин по миссиям (IDLE/STUDY_FOCUS/CODING_WORK/GAMING_REST — семантика decay по RFC-0001). *AC:* unit-тесты модели decay на эталонных траекториях счёта; вмешательство инициируется только при пересечении 50 с учётом затухания.
- **FR-015** (proactivity, Ф2, Must, PAD §5.1): В миссии GAMING_REST проактивность ДОЛЖНА быть принудительно 0%. *AC:* автотест на гейминг-корпусе — 0 проактивных вмешательств.
- **FR-016** (proactivity, Ф2, Must, ARCH §6): Scorer ДОЛЖЕН замораживать таймер стагнации вкладки при активном видеопотоке в сфокусированном окне (видеолекция ≠ фрустрация). *AC:* сценарий «лекция 20 мин без скролла» — счёт не достигает порога.
- **FR-017** (proactivity, Ф2, Should, research): Должен существовать per-session cap вмешательств и kill-switch (auto-degrade в reactive-only) при acceptance < 15% по когорте. *AC:* телеметрическая метрика `proactivity_acceptance_rate` определена в metric registry.

### FR-MEM — Трёхуровневая память

- **FR-018** (memory, Ф2, Must, PAD §4): Уровень 1 — RAM-сессия 2–4 ч (кольцевой буфер: буфер обмена, окна, реплики) по SQL-схеме `session_memory_tier1` из RFC-0001; передаётся в контекстное окно облачной LLM.
- **FR-019** (memory, Ф2, Must, PAD §4.2): Уровень 2 — ночная архивация: через MCP (FastMCP, транспорта stdio/Streamable HTTP/SSE) создаётся Markdown-дневник в Obsidian/Notion (изученное, код, трудности). *AC:* 100% успешная ночная генерация .md-отчёта на dogfood-выборке; retry при `sync_status = FAILED`.
- **FR-020** (memory, Ф2, Must, PAD §4.3): Уровень 3 — векторный граф знаний (VectorDB, LanceDB/Qdrant Embedded) для RAG-ответов без галлюцинаций («Как мы настроили парсер?»). *AC:* эталонный набор вопросов — ответ содержит факт из tier3 с полем `last_recalled_at` обновлённым.
- **FR-021** (memory, Ф2, Must, GDPR): Right to erasure: удаление профиля и памяти реализуемо локально (SQLite + VectorDB + staging purge) без обращения в поддержку.

### FR-SR / FR-MCP — Semantic Router, SOP, MCP-хаб

- **FR-022** (router_and_sops, Ф2 Must (черновики) / Ф3 Must (автозапуск), PAD §7): Генерация SOP: LLM формирует Черновик (Blueprint) с кнопками [Утвердить рецепт] / [Изменить]; после утверждения компилируется в жёсткий Python-скрипт + вектор триггера в VectorDB.
- **FR-023** (router_and_sops, Ф3, Must, RFC-0001): Semantic Router ДОЛЖЕН перехватывать событие до облака; при косинусном совпадении >= 0.98 — автоисполнение скрипта без LLM; 0.90–0.98 — карточка подтверждения; < 0.90 — свободный диалог LLM. *AC:* golden-набор триггеров: при >= 0.98 в телеметрии отсутствуют вызовы облачной LLM (событие `BLUEPRINT_MATCHED_98`); выполняются шаги скрипта в эталонном порядке.
- **FR-024** (router_and_sops, Ф3, Must, OWASP LLM01/LLM06 / ARCH §6): SOP-компилятор ДОЛЖЕН транслировать шаги исключительно в вызовы типизированных MCP-инструментов и методов Tier 1–3 (AST-валидация, sandbox); даже при компрометации промпта рецепт НЕ МОЖЕТ обойти карантин Archie_Staging или выполнить несанкционированное удаление. *AC:* adversarial-набор промптов — 0 escape-инцидентов (red-team suite из Threat Model).
- **FR-025** (mcp_hub, Ф2 Should / Ф3 Must, PAD §4.2): MCP-хаб поддерживает reference-серверы `obsidian_vault_server`, `notion_sync_server`, `git_automation_server` с явными allowlist (паттерн официальных MCP reference servers).
- **FR-026** (mcp_hub, Ф4, Must, PAD §10): Enterprise-серверы `enterprise_jira_slack` (Jira-карточки, Slack-отчёты тимлиду) в корпоративном контуре.

### FR-STG / FR-PERM — Действия и безопасность

- **FR-027** (staging-fs, Ф2, Must, PAD §6.2): Очистка рабочего стола ДОЛЖНА физически не использовать системный Delete: 100% перемещений — в `~/Archie_Staging`; нужные программы закрепляются в меню «Пуск»/панели задач. *AC:* интеграционный тест «рабочий стол» — 0 вызовов API удаления, все пути назначения в staging; риск потери данных = 0.
- **FR-028** (permission_tiers, Ф1 Must (Tier 0/1) → Ф2 Must (Tier 2) → Ф3 Must (Tier 3), PAD §6.1): Tier 0/1 — автономные безопасные действия (музыка, поиск, чтение логов) без спроса; Tier 2 — критические (удаление, письма, git push) через approval-карточку с окном отмены 3–5 с и rollback через staging-commit; Tier 3 — Context Workspaces по запросу «Я хочу учиться» (закрыть развлекательные вкладки, открыть IDE/PDF, включить Lo-Fi).
- **FR-029** (staging-fs, Ф3, Must, research): Файловые изменения Tier 2 ДОЛЖНЫ идти через staging-зоны с commit/rollback. *AC:* откат подготовленного, но неутверждённого действия возвращает ФС в исходное состояние (хэш-сравнение дерева).

### FR-SW — Soft Widget / UI

- **FR-030** (soft_widget, Ф2, Must, PAD §5.3): Двухступенчатое вмешательство: пульсирующий виджет у края экрана; 3–5 с на беззвучную отмену; затем мягкая стартовая фраза. *AC:* отмена в окне — голос не включается; пропуск — фраза начинается; тайминг подтверждён логами (`widget_cancelled_by_user` в `frustration_telemetry`).
- **FR-031** (soft_widget, Ф1 Must (каркас) / Ф2 Must (поведение), ARCH §2.1): Виджет ОБЯЗАН рендериться поверх полноэкранных игр, не перехватывая ввод фоновых приложений (dual-window, Always-on-top, Transparent, Undecorated, Show Desktop immunity, resize-on-activation только для Tier 2 карточек). *AC:* гейминг-сценарий — виджет видим поверх fullscreen, клики по игре проходят, Win+D не сворачивает оверлей.
- **FR-032** (desktop-ui, Ф2 Must, WCAG 2.2 AA): Approval-карточки и менеджер рецептов ДОЛЖНЫ быть оперируемы с клавиатуры, с достаточным контрастом и reduced-motion режимом; голосовой вывод дублируется текстом (captioning).
- **FR-033** (desktop-ui, Ф1 Must, PAD §9): Онбординг Path A (15-мин голосовое интервью) и Path B (тихое наблюдение, минимум активности) — оба достигают первого полезного действия <= 10 минут; конверсия A/B — инструментированная метрика GTM.

### FR-PII — Анонимизация

- **FR-034** (security, Ф2 Must (v1) / Ф4 Must (enterprise-гарантии), PAD §3.2 / 152-FZ / GDPR): Перед любым облачным вызовом текстовый слепок ДОЛЖЕН проходить PII Sanitizer (regex-каскад + локальная ONNX NER): ключи API, пароли, карты, проприетарный код → теги `[REDACTED_API_KEY]`, `[REDACTED_FINANCIAL_DATA]`. *AC:* adversarial suite: named-категории redacted с целевыми precision/recall (значения — QA-документ); в network-assertion интеграционных тестов наблюдаются только санированные payload; 0 сырых кадров/аудио в egress (NFR-006).
- **FR-035** (security, Ф2 Must, research): Санитайзер ДОЛЖЕН маскировать и third-party идентификаторы (чужие сообщения в чатах/почте на экране).

## 7. User Stories с критериями приёмки (выборка ключевых)

Полный backlog живёт в issue-трекере (labels = FR-ID, milestone = фаза); здесь — истории, определяющие ядро продукта. Формат: «Как <персона>, я хочу <возможность>, чтобы <ценность>» + Given/When/Then.

- **US-101 (P1, FR-014/FR-030, Must, Ф2).** Как студент, я хочу, чтобы ассистент заметил моё «залипание» и предложил помощь мягко, чтобы я вернулся к подготовке без чувства, что меня контролируют. *Given* миссия STUDY_FOCUS и накопленный счёт фрустрации >= 50, *When* срабатывает внутренний монолог, *Then* появляется Soft Widget, и в течение 3–5 с я могу отменить разговор беззвучно; при отмене счёт intervention не считается «принятым».
- **US-102 (P3, FR-015/FR-031, Must, Ф2).** Как геймер, я хочу нулевой проактивности во время игры, чтобы ничто не ломало immersion. *Given* запущен fullscreen-титул и миссия GAMING_REST, *When* проходят 2 часа, *Then* 0 проактивных вмешательств, виджет не перехватывает клики, FPS-просадка от оверлея в пределах погрешности.
- **US-103 (P2, FR-009, Must, Ф1).** Как начинающий разработчик, я хочу перебивать Archie голосом, как в живом разговоре, чтобы не слушать уже понятное. *Given* Archie озвучивает длинное объяснение, *When* я начинаю говорить «стоп, я понял», *Then* TTS останавливается за < 200 мс и микрофон захватывает мою реплику.
- **US-104 (P2, FR-028/FR-027, Must, Ф2).** Как разработчик, я хочу, чтобы Archie готовил коммит, но пушил только после моего подтверждения, чтобы исключить случайные потери. *Given* активен Blueprint «коммит после кодинга», *When* он срабатывает, *Then* отображается Tier 2 approval-карточка с 3–5 с окном отмены; до подтверждения изменения лежат в staging-зоне с возможностью rollback.
- **US-105 (P1, FR-023, Must, Ф3).** Как студент, я хочу, чтобы утверждённые «рецепты» выполнялись одинаково каждый раз, чтобы рутина исчезла без сюрпризов. *Given* утверждён SOP «завершение учебного дня», *When* триггер совпал с эмбеддингом на >= 0.98, *Then* скрипт исполняется локально без вызова облачной LLM и с предсказуемыми шагами (телеметрия: `BLUEPRINT_MATCHED_98`, 0 cloud-вызовов).
- **US-106 (все, FR-006, Must, Ф1).** Как пользователь со слабым ноутбуком и нестабильным интернетом, я хочу, чтобы ассистент деградировал изящно, чтобы не терял напарника офлайн. *Given* облачный провайдер недоступен (API_TIMEOUT), *When* я задаю голосовой вопрос, *Then* локальная SLM 1.5B отвечает голосом с тем же характером, а сложные функции (код, математика) явно отключаются.
- **US-107 (P4, FR-026/FR-034, Must, Ф4).** Как тимлид, я хочу, чтобы стажёрский онбординг шёл через Archie, а данные не покидали периметр компании. *Given* enterprise-конфигурация On-Premise, *When* стажёр работает, *Then* весь LLM-инференс идёт на внутренних серверах, PII-санитайзер маскирует 100% ключей/кода, а HR видит только анонимные тепловые карты Burnout Tracker.

INVEST-проверка: каждая история независима в рамках фазы, договороспособна (scope фазы), оценяема (story points проставляет команда), малая (фаза-гейт), тестируема (Gherkin против наблюдаемого поведения — не внутреннего состояния) и ценностна (трассируется на персону).

## 9. Release Criteria по фазам (Definition of Done / Exit Gates)

**MVP Alpha (выход):**
- Внутренний dogfood: ежедневная активность команды на одной платформе (Windows).
- Barge-in p95 < 200 мс на целевом железе; OCR p95 <= 250 мс; VAD 85–100 мс (> 95%); RAM Idle 150 МБ (гейты CI зелёные).
- Graceful degradation продемонстрирован (FR-006); 0 инцидентов самопрерывания TTS в double-talk-тестах.
- Path A onboarding до первого полезного действия <= 10 мин.
- Audio-loopback риг и RAM-гейты существуют и обязательны в CI с этой фазы.

**B2C Beta (выход):**
- 100–500 внешних пользователей; оба пути онбординга (A и B) работают; телеметрия opt-in собрана.
- 0 проактивных вмешательств в GAMING_REST; порог фрустрации 50 с корректным decay; окно отмены 3–5 с работает (телеметрия `widget_cancelled_by_user`).
- Ночные отчёты Obsidian/Notion >= 99%; PII Sanitizer проходит adversarial suite; network-assertion: только санированные payload.
- RAM Peak 655 МБ (CI-гейт +10%); tier-2 approval с rollback испытан на реальных пользователях.

**v1.0 Production (выход):**
- Публичный запуск, мультиплатформенность (Windows + macOS + Linux), auto-update без нарушения Barge-in в текущей сессии.
- Semantic Router: на golden-наборе при >= 0.98 — 0 облачных вызовов; 0 escape-инцидентов sandbox (red-team suite).
- Инсталлятор ~8 МБ; RAM Offline 1450 МБ; WCAG 2.2 AA-аудит пройден.
- KPI: DAU/retention/acceptance >= целей (значения зафиксированы при scope freeze Beta).

**v2.0 Enterprise (выход):**
- Пилот с 1–2 корпоративными клиентами; enterprise_jira_slack MCP; SSO/admin console; tamper-evident audit log.
- On-Premise/VPC-вариант: работа внутри периметра без внешнего интернета (замер на пилоте).
- SOC 2 Type II — процесс инициирован для облачных компонентов (критерий: аудит запущен); Burnout Tracker — только анонимные агрегаты с прозрачностью для сотрудника.

## 10. Constraints, Assumptions, Dependencies

- **Стек (неизменяемые ограничения):** Tauri v2 (dual-window оверлей, ~8 МБ инсталлятор), Rust-ядро (tokio, event bus, OS-hooks, staging-fs), Python 3.11+ (archie-engine: ONNX-инференс, MCP, SOP), React 19/TS 5.8, SQLite (WAL) + VectorDB (LanceDB/Qdrant Embedded), контракты в `contracts/`.
- **Архитектурные guardrails:** single-process audio loop (оговорён дизайн barge-in-тестов — FR-008); `set_ignore_cursor_events` «всё или ничего» → dual-window схема обязательна для FR-031; глобальные хоткеи только через штатный плагин Tauri (rdev-подход запрещён из-за crash-риска на macOS).
- **Допущения:** облачные провайдеры остаются доступны и API-совместимы с abstraction-слоем; целевое железо >= 8 ГБ RAM ([uncertain] floor для 655 МБ-бюджета); локальные модели (RapidOCR ~80 МБ, Silero VAD 1–2 МБ, Piper, SLM 1.5B GGUF) лицензионно чисты для дистрибуции.
- **Зависимости:** RFC-0001 (SLA-канон), Threat Model (контроли для FR-024/FR-034), QA Strategy (тест-планы по FR-ID), Business Model (cloud cost ceilings), GTM (метрики активации).

## 12. Open Questions

1. **Микс cloud-LLM по фазам:** каким тирам пользователей доступен облачный инференс; потолок cost/MAU — вход от Business Model.
2. **Рынок запуска:** RU-first (клин ЕГЭ, 152-FZ) vs EN/EU-first (TAM больше, но AI Act на emotion recognition) — влияет на regulatory FR и географию Beta.
3. **Семантика гейта фрустрации:** точные cooldown-значения и трактовка порога 50 (suppress vs trigger) — требует sign-off RFC-0001. [uncertain]
4. **Hardware floor** для бюджета 655 МБ (8 ГБ RAM? 4 ГБ?) — влияет на выбор OCR/ASR моделей.
5. **Open-core граница:** какие модули (semantic router? SOP-библиотека? MCP-серверы?) становятся open source — влияет на enterprise-дифференциацию.
6. **Age gating / родительский консент** для студенческого сегмента (RU до 14, EU 13/16). [uncertain]
7. **SOP-библиотека в Beta:** курируемая редакционная подборка или только user-generated из Path B.
8. **Pivot-триггеры B2B:** точные пороги (conversion %, inbound count); v2.0 — только on-prem или также SaaS.
9. **Телеметрия:** какие метрики собираемы при opt-in privacy без деградации надёжности KPI.
10. **EU AI Act классификация** frustration scoring (emotion recognition) — юридическая экспертиза до EU-запуска. [uncertain]

## 13. Traceability (сводно)

Каждая FR трассируется: персона → user story → фаза → модуль монорепо → контракт RFC-0001/PAD. Итоговая матрица генерируется из issue-трекера (labels = FR-ID, milestone = фаза); инварианты ревью: (a) ни одна FR без модуля-владельца, (b) ни одна FR без персоны-источника, (c) каждое квантифицированное число цитирует RFC-0001. Ключевые связи: FR-008/009/010 → аудио-контракты RFC-0001 (sequence, FORCE_STOP_AUDIO); FR-002 → OCR timing; NFR-004 → RAM-таблица + WorkerHealthMetrics; FR-014 → decay-уравнение; FR-023 → SOP cosine threshold; FR-004/FR-018–020 → event envelope и SQL DDL RFC-0001. Практика: CI-скрипт сравнивает SLA-числа PRD и RFC-0001 (grep + diff) — ловит drift дёшево.
