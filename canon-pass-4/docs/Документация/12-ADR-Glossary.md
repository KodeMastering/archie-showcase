# 12 — ADR-лог архитектурных решений и глоссарий проекта Archie

**Статус:** Accepted (документ — часть комплекта, №15 из docs/)
**Аудитория:** инженеры (Rust/Python/TS), архитектор, будущие контрибьюторы и инженеры B2B-клиентов (Phase 4)
**Назначение:** институциональная память репозитория. Документ фиксирует, **почему** приняты ключевые технические решения (чтобы они пережили ротацию команды и не переобсуждались с нуля), и закрепляет **единый словарь** терминов Archie для всех документов комплекта и кодовых идентификаторов монорепозитория.

Числа и структура монорепо в этом документе каноничны и скопированы из RFC-0001 без перефразирования: Barge-in < 200 мс; VAD 85–100 мс (точность > 95%); OCR ~200 мс (185 мс эталон); RAM 150/655/1450 МБ (Idle/Peak/Offline); порог фрустрации 50 (S_max = 100, полураспад 20/15/5/1 мин); совпадение SOP-триггера >= 0.98; окно отмены Soft Widget 3–5 с; инсталлятор ~8 МБ (без весов моделей).

## ЧАСТЬ A. ADR-лог

### A.1. Как устроены ADR в Archie

**Что является ADR.** ADR (Architecture Decision Record) фиксирует решение, которое дорого обратить: стоимость отката больше одного спринта ИЛИ ответ на вопрос «почему сделано так?» занимает больше пяти минут у нового члена команды. Тривиальные решения (выбор lint-плагина) живут в описаниях PR. Контракты (сигнатуры, схемы, бюджеты) живут в RFC; ADR хранит только **обоснование** и ссылается на RFC по номеру раздела.

**Формат** — MADR-lite (производная от [MADR](https://github.com/adr/madr), восходящая к эссе Michael Nygard «Documenting Architecture Decisions»):

```
# ADR-NNNN: <решение как утверждение, не существительное>
- Статус: Proposed | Accepted | Superseded by ADR-MMMM
- Дата / Фаза / Затрагиваемые модули
- Контекст (силы, ограничения, цитаты бюджетов RFC-0001)
- Решение (одно предложение + обоснование)
- Последствия (позитивные / негативные)
- Альтернативы (и почему отклонены)
- Ссылки (RFC-0001, PAD, смежные ADR) / Compliance-хуки (тесты/линты)
```

**Дисциплина:** одна запись — одно решение; нумерация монотонная, номера не переиспользуются; принятые ADR **не редактируются на месте** — только суперседируются новой записью с двусторонней ссылкой. Это не только инженерная гигиена: в Phase 4 git-история `docs/adr/` используется как evidence для SOC 2 аудита изменений. ADR мержатся через PR с ревью, а не дописываются постфактум одним человеком.

#### ADR-001: Использовать Tauri v2, а не Electron, для desktop shell

**Статус:** Accepted. **Фаза 1.** **Модули:** `apps/desktop-ui/`, `crates/archie-shell/`.

**Контекст.** Archie — постоянно живущий фоновый ассистент. RFC-0001 требует уложиться в 150 МБ RAM в idle (1.83% от 8 ГБ) — весь бюджет Shell+UI не должен съедаться рантаймом. Electron на базовом плавающем окне потребляет порядка ~200 МБ RAM и даёт инсталлятор ~120 МБ; это сопоставимо со всем idle-бюджетом клиента. Дополнительно спецификация требует прозрачный always-on-top оверлей с пропуском кликов.

**Решение.** Графический рантайм — Tauri v2 (Rust-ядро + системный WebView: WebView2 / WKWebView) с React 19 / TypeScript 5.8 и легковесным SolidJS + UnoCSS для микро-виджетов. Инсталлятор ~8 МБ против ~120 МБ, экономия ~200 МБ RAM, а Rust-ядро shell'а совпадает с языком системных крейтов.

Ключевой компромисс зафиксирован явно: в Tauri v2 `set_ignore_cursor_events` работает «всё или ничего» — окно либо полностью перехватывает мышь, либо полностью её пропускает, без выборочной фильтрации по альфа-каналу. Поэтому применяется **двухоконная архитектура (Dual-Window)**: компактный `widget-overlay` (Always-on-top, Transparent, Undecorated, resize-on-activation только при показе карточек Tier 2) и предсозданный скрытый `main-dashboard` (`prevent_close()` + `hide()`, DOM Virtualization 65 МБ → 16 МБ). Глобальные хоткеи — только через штатный плагин Tauri с детектором конфликтов (низкоуровневый `rdev` на macOS конфликтует с CGEventTap и роняет приложение).

**Последствия.** Позитив: инсталлятор ~8 МБ, на порядок ниже RAM, единый Rust-стек, живой IPC через `invoke`/events. Негатив: зависимость от системных WebView (разное поведение платформ, двойная подписка `ScaleFactorChanged` для HiDPI), ограничение пропускания кликов вынуждает держать два окна и синхронизировать их состояния.

**Альтернативы.** Electron — отклонён по RAM/размеру при приемлемой зрелости экосистемы; чистый Qt/egui — отклонён из-за стоимости UI-разработки виджетов и карточек против React-стека; Flutter Desktop — отклонён как второй тяжёлый рантайм с собственным движком рендеринга.

**Compliance-хуки:** RAM-регрессия idle 150 МБ (RSS-профилирование через `ReportWorkerHealth`), гейт CI на размер инсталлятора.

#### ADR-002: Единый внутрипроцессный аудио-цикл (Single-Process Audio Loop)

**Статус:** Accepted. **Фаза 1.** **Модуль:** `services/archie-engine/src/archie_engine/audio_loop/`.

**Контекст.** Бюджет Barge-in из RFC-0001 — полная остановка голоса ассистента < 200 мс. Из них детекция речи Silero VAD занимает 85–100 мс (< 1 мс на 30-мс чанк, точность > 95%), ещё ~45 мс — частичная транскрипция STT и семантический Turn Detection. На «клей» остаётся < 100 мс — межпроцессный хоп сигнала остановки через очередь/сокет эту норму срывает. Хуже того: при выносе TTS в отдельный от микрофонного захвата процесс джиттер планировщика ОС и дрейф буферов разрушают по-сэмпловое выравнивание референсного сигнала для WebRTC AEC3, фильтр отказывает при double-talk, и Archie начинает слышать собственный голос из колонок, ложно генерируя `FORCE_STOP_AUDIO` и прерывая себя на первой фразе.

**Решение.** Весь голосовой тракт — захват микрофона, вывод TTS, эхоподавление AEC3 (биндинги livekit), гейтинг Silero VAD, детекция вздохов, потоковый STT (Sherpa-ONNX, Kroko ASR / Whisper) и синтез Piper TTS — работает в одном процессе `archie-engine` на выделенном высокоприоритетном потоке с **единым тактовым генератором аудиоустройства** (sounddevice, фрейм 30 мс). Референс TTS подаётся в AEC3 по-сэмплово синхронно (`write_farend_reference`), а сигнал остановки — прямой вызов в общем адресном пространстве: сброс буфера за микросекунды, остановка синтеза строго внутри SLA < 200 мс. Только уведомление шины (`PublishEvent(FORCE_STOP_AUDIO)`) идёт асинхронно и не на критическом пути.

**Последствия.** Позитив: AEC работает при double-talk, отсутствие самопрерываний, детерминированный Barge-in. Негатив: аудио-поток нельзя рестартовать, не затронув весь тракт; сбой (segfault в C++-биндингах) роняет голос целиком — компенсируется супервизией в Rust-ядре и рестартом воркера.

**Альтернативы.** Разнос TTS/STT/VAD по отдельным микросервисам — отклонён как раз из-за разрушения выравнивания сэмплов AEC3 и IPC-задержек; полностью Rust-нативный аудио-тракт — отклонён на Phase 1 из-за отсутствия зрелых биндингов AEC3/Piper/Sherpa (пересмотр возможен позже — см. бэклог).

**Compliance-хуки:** интеграционный тест Barge-in через loopback (подача референсного TTS + наложенной реплики), метрики `stop_latency_us` в `ForceStopAudioPayload`.

#### ADR-003: IPC через UDS 0600 / Named Pipes ACL + gRPC и 16 МБ shared memory, а не TCP loopback

**Статус:** Accepted. **Фаза 1.** **Модули:** `crates/archie-event-bus` (`ipc_server.rs`, `shm_ring.rs`), `contracts/ipc_bridge.proto`.

**Контекст.** Rust-ядро (Host Daemon: шина, хуки ОС, staging-FS) и Python-воркер `archie-engine` должны обмениваться событиями и экранными кадрами (2560×1440). Транспорт TCP loopback (127.0.0.1) для десктопного приложения уровня ОС порождает три проблемы: (1) слушающий TCP-порт на Windows вызывает предупреждения брандмауэра, а без сетевого адаптера привязка падает; (2) локальный TCP-сокет доступен другим процессам машины — требуется дополнительное криптографическое рукопожатие против перехвата управления; (3) сетевой стек TCP/IP проигрывает локальным IPC-каналам по накладным расходам на крупных сообщениях.

**Решение.** Двухплоскостная гибридная топология. **Control/Event Plane:** gRPC (tonic ↔ grpcio.aio) поверх Unix Domain Socket `/tmp/archie-ipc-{uid}.sock` с правами 0600 (macOS/Linux) и поверх named pipe `\\.\pipe\archie-ipc-{session_id}` с ACL уровня пользователя и `reject_remote_clients(true)` (Windows — у tokio асинхронный UDS на Windows ограничен, native-примитив это `tokio::net::windows::named_pipe`). Контракт — `contracts/ipc_bridge.proto`: `StreamEvents` (полнодуплексный поток `EventEnvelope`), `TriggerZSenseOcr`, `ExecuteSystemAction`, `ReportWorkerHealth`. **Data Plane (zero-copy):** пул разделяемой памяти `archie_shm_vision` фиксированного размера 16 МБ для пиксельных кадров активного окна; по gRPC передаются только дескриптор слота и метаданные (`ShmFrameDescriptor`: `shm_slot_id`, width, height, `scale_factor`, `seq_lock_version`). Python читает кадр через `multiprocessing.shared_memory` поверх `numpy.ndarray` — сериализация пикселей через Protobuf исключена.

**Последствия.** Позитив: нет брандмауэр-промптов, доступность канала enforced правами ОС (0600/ACL), копирование кадров устранено, RPC-семантика и типизация из `.proto`. Негатив: платформенно-зависимый код транспорта (компилируемые ветки `#[cfg(unix)]/#[cfg(windows)]`), ручное управление жизненным циклом shm-региона и seqlock-версионированием.

**Альтернативы.** TCP loopback — отклонён (см. контекст); чистый UDS без gRPC — отклонён из-за отсутствия типизированного RPC и стриминговой семантики; D-Bus — отклонён как Linux-only и слишком медленный для data plane.

**Compliance-хуки:** юнит-тесты bind/permissions (0600/ACL), тест zero-copy доставки кадра в `archie-engine`.

#### ADR-004: LanceDB embedded как векторное хранилище, а не Qdrant server

**Статус:** Accepted. **Фазы 1–3.** **Модули:** `storage/vector_store.lancedb/`, `router_and_sops/`, `memory/tier3_vector_graph.py`.

**Контекст.** Tier 3 долговременной памяти и Семантический роутер требуют локального ANN-поиска по эмбеддингам триггеров SOP и фактов графа знаний, при совпадении >= 0.98 включающем обход облачной LLM. Бюджет RFC-0001: idle 150 МБ / peak 655 МБ — **никакого дополнительного серверного процесса** в постоянной памяти быть не может; целевая машина — ноутбук 8 ГБ без dGPU. Также важно mmap-чтение индекса с диска (см. матрицу RAM: память/роутер держат 18/64 МБ за счёт disk-backed mmap и ленивого эмбеддера TTL = 120 с).

**Решение.** LanceDB в embedded-режиме (in-process, Rust-native, без демона), персистентность — локальные файлы в `storage/vector_store.lancedb/` поверх Arrow/mmap. Эмбеддинги — локальный FastEmbed INT8 (~46 МБ, TTL-выгрузка). Доступ из Python через официальный SDK в том же воркере `archie-engine`.

**Последствия.** Позитив: ноль дополнительных процессов, RAM-футпринт ограничен mmap-страницами, файловая персистентность попадает в единый `storage/`, комплексные фильтры (status = 'APPROVED_ACTIVE') поверх ANN-поиска. Негатив:embedded-режим означает, что падение воркера затрагивает и индекс (восстановление из диска); LAN-доступа нет — что для single-user клиента и не требуется; экосистема моложе Qdrant.

**Альтернативы.** Qdrant в server-режиме — отклонён: резидентный демон не лезет в бюджет 150/655 МБ; Qdrant embedded — рассмотрен, но Python-first и слабее интеграция с Rust-стеком; pgvector — отклонён, требует сервера Postgres; sqlite-vec — привлекательная лёгкость, но на момент решения уступал по зрелости ANN и возможностям фильтрации (пересмотр при смене требований — см. бэклог); Chroma — отклонён как Python-центричный с лишними зависимостями.

**Compliance-хуки:** RAM-регрессия пикового профиля 655 МБ; модульные тесты `semantic_router.py` (совпадение >= 0.98, обход LLM).

#### ADR-005: Песочница SOP — AST-валидация и только MCP-инструменты, без исполнения сгенерированного LLM кода

**Статус:** Accepted. **Фаза 3.** **Модули:** `router_and_sops/sop_sandbox_runner.py`, `ast_validator.py`, `mcp_hub/`.

**Контекст.** Утверждённые «Умные черновики» (Smart Blueprints) компилируются в Python-скрипты, которые Семантический роутер исполняет автоматически при совпадении >= 0.98 — в обход LLM. Значит, даже при компрометации промпта (инъекция через экран/текст) скомпилированный рецепт не должен уметь исполнять произвольные системные вызовы: ни удалить файлы, ни выйти в сеть, ни обойти карантин `Archie_Staging`.

**Решение.** Никогда не исполняется код, сгенерированный LLM «как есть». Компилятор рецептов транслирует шаги черновика **исключительно** в вызовы строго типизированных инструментов локальных MCP-серверов (`git_automation_server`, `obsidian_vault_server` и т.д.) и методов Action Engine уровней Tier 1–3. Первые ворота — статическая **AST-валидация**: скрипт парсится и отклоняется до исполнения, если содержит `import`, `exec`/`eval`/`compile`, `__import__`, file I/O (`open`), `socket`/`subprocess` — или любой вызов функции вне whitelist'а MCP tool-call DSL. Вторые ворота — runtime-confinement песочницы; третьи — гейт Permission Tiers перед любым побочным эффектом (см. ADR-011).

**Последствия.** Позитив: surface атаки сжимается до конечного списка типизированных инструментов; детерминизм исполнения SOP; независимость безопасности от качества выходов LLM. Негатив: выразимость рецептов ограничена DSL — нестандартные сценарии требуют расширения набора MCP-инструментов (процедура через ревью), валидатор нужно поддерживать синхронно с DSL.

**Альтернативы.** Исполнение сгенерированного кода в изолированном контейнере/Docker — отклонено: тяжело для end-user ноутбука и не даёт детерминизма рецепта; WASM-песочница — отложена как потенциальный рантайм второго поколения (та же проблема выразимости); «доверие + аудит постфактум» — отклонён как неприемлемый риск удаления данных.

**Compliance-хуки:** security-тест-сьют песочницы (перечень запрещённых конструкций, см. QA-стратегию и STRIDE-записи в Threat Model), аудит `action_audit_log`.

#### ADR-006: Абстракция облачных провайдеров (DeepSeek / OpenAI / Gemini), переключаемых конфигурацией

**Статус:** Accepted. **Фаза 1.** **Модули:** `contracts/`, `services/archie-engine/llm_clients/cloud_gateway.py`.

**Контекст.** PAD требует cloud-гибридности без vendor lock-in: DeepSeek (эконом), OpenAI, Google Gemini (gemini-2.5-flash/pro) — равноправные варианты, выбираемые по цене/доступности/юрисдикции, включая полный уход в On-Premise контур на Phase 4. Жёсткое кодирование одного провайдера сделало бы смену кодовым изменением во всех точках вызова.

**Решение.** Единый интерфейс провайдера фиксируется в `contracts/` (единый вход/выход по схеме, стриминг токенов, сигнатура ошибок → `ApiTimeoutPayload`). `cloud_gateway.py` реализует адаптеры DeepSeek / OpenAI / Gemini как конфигурируемые реализации; добавление нового провайдера или смена основного — **нулевые изменения вне `contracts/` и конфига**. Маршрутизация per-call: разные классы запросов (Inner Monologue, генерация черновика SOP, менторство) могут идти к разным провайдерам/моделям; решения деградации (ADR-007) опираются на нормализованные сигнатуры ошибок, а не на специфику вендора.

**Последствия.** Позитив: свобода выбора по стоимости и доступности, готовность On-Premise (провайдер = корпоративный сервер), унифицированный сбор телеметрии ошибок. Негатив: слой абстракции усредняет возможности — вендор-специфичные фичи (особые tool-call форматы, мультимодальность) требуют явного расширения контракта; conformance-тесты каждого адаптера обязательны, иначе «совместимость» станет фикцией.

**Альтернативы.** SDK-специфичный код у каждого call-site — отклонён (vendor lock-in); единый шлюз-сервис (LiteLLM-класс) — отклонён как лишний процесс/зависимость и потеря контроля над retry-политикой при деградации.

**Compliance-хуки:** провайдер-conformance-сьют (одинаковые промпты/схемы in/out для каждого адаптера), тест маршрутизации per-call.

#### ADR-007: Graceful Degradation с локальным фолбэком 1.5B (Qwen2.5-1.5B Q4_K_M GGUF, mmap по требованию)

**Статус:** Accepted. **Фаза 1.** **Модули:** `llm_clients/local_1_5b_fallback.py`, `crates/archie-event-bus/graceful_degradation.rs`, `models/fallback_llm/`.

**Контекст.** Офлайн — спроектированное состояние UX, а не ошибка. При `API_TIMEOUT` клиент обязан сохранить голос, характер и локальные действия (сортировка файлов, управление музыкой, запуск программ), прозрачно предупредив о временном отключении тяжёлых моделей. Целевая машина — 8 ГБ RAM, без dGPU (локальные агентские сборки класса Jarvis требуют 16–24 ГБ VRAM и отсекают ~90% аудитории). Офлайн-потолок RAM по RFC-0001 — 1450 МБ (17.70% от 8 ГБ).

**Решение.** Резервная модель — **Qwen2.5-1.5B-Instruct в формате GGUF, квантование Q4_K_M (~1080 МБ с контекстом 2048 токенов)**, исполняется на CPU через llama-cpp-python. В онлайн-режиме — 0 МБ RAM: файл лежит на диске (`models/fallback_llm/qwen2.5_1_5b_q4_k_m.gguf`). По сигналу `API_TIMEOUT` модуль `graceful_degradation.rs` выставляет `offline_fallback_active = 1`, предварительно вытесняя RapidOCR (145 МБ) и ONNX NER (66 МБ), и модель **мапится в память через mmap** по требованию. Восстановление сети — обратный переход с выгрузкой. Оркестрация памяти — через `ReportWorkerHealth` / `MemoryControlDirective` (см. ADR-008-границу и Lazy Loading контроллер).

**Последствия.** Позитив: полный офлайн без dGPU, укладка в 1450 МБ за счёт вытеснения, мгновенный (не «холодный» на диске уже лежит) переход. Негатив: качество локальной 1.5B заведомо ниже облачных моделей — сложная математика и генерация кода в офлайне деградируют (и честно озвучиваются пользователю); mmap 1080 МБ конкурентен страницам остальных моделей — порядок вытеснения критичен.

**Альтернативы.** Полное отключение функций в офлайне — отклонено, разрушает ценность «симбиота»; гибрид с 7B+ моделью — не лезет в офлайн-бюджет RAM; постоянная резидентность 1.5B — отклонена (0 МБ онлайн важнее).

**Compliance-хуки:** симуляционный тест `API_TIMEOUT` → переход без потери голоса; RAM-профиль offline 1450 МБ в 4-часовой сессии.

#### ADR-008: Гибридное разделение Rust + Python с gRPC-границей

**Статус:** Accepted. **Фаза 1.** **Модули:** все `crates/`, `services/archie-engine/`, `contracts/`.

**Контекст.** Системные требования (перехват событий ОС, управление окнами, файловая безопасность, шина с микросекундной маршрутизацией) требуют системной производительности Rust; ML-требования (ONNX-инференс, векторные БД, MCP-серверы, аудио-биндинги, рецепты автоматизации) живут в Python-экосистеме. Монолит на одном языке — либо системная часть задыхается (Python), либо ML-часть пишется с нуля на несуществующих биндингах (Rust). Изоляция отказов также требует, чтобы рестарт Python-модуля (обновление весов OCR, переподключение MCP-сервера) не ронял системный трей и оверлей.

**Решение.** Разделение по контурам: **Rust** — `archie-shell` (окна, трей, single-instance, HiDPI), `archie-event-bus` (брокер, IPC-сервер, graceful degradation), `archie-os-hooks` (active window, accessibility tree, clipboard, input heuristics, media session), `archie-stagingfs` (безопасная ФС, permission tiers, audit). **Python** — весь `archie-engine`: Z-Sense OCR, PII-санитайзер, аудио-цикл (ADR-002), проактивность, память Tier 1–3, роутер SOP, LLM-клиенты, MCP hub. Граница — gRPC поверх UDS/Named Pipes + shared memory (ADR-003), контракт `contracts/ipc_bridge.proto`; Rust — сервер и супервизор, Python — клиент-воркер; здоровье и RAM — через `ReportWorkerHealth` → `MemoryControlDirective`.

**Последствия.** Позитив: каждый язык силён в своей зоне; супервизия и Restart-изоляция воркеров; контракты типизированы и генерируются на 3 языка (ADR-012). Негатив: два toolchain'а (Cargo workspace + uv/pyproject), двойная CI-матрица; владение отладкой на границе (сериализация, тайминги) требует понимания обеих сторон.

**Альтернативы.** Всё на Rust (PyO3 для ML) — отклонено на Phase 1: отсутствие зрелых обвязок для sherpa/Piper/FastMCP/LanceDB-python экосистемы; всё на Python — отклонено по производительности и надёжности системных хуков; WASM-модули — отклонены как несоответствие системным API.

**Compliance-хуки:** тест рестарта `archie-engine` без падения трея/оверлея; линт границ (запрет прямых вызовов через границу мимо контрактов).

#### ADR-009: Staging-зоны вместо удаления (Archie_Staging, запрет системного вызова Delete)

**Статус:** Accepted. **Фаза 2.** **Модуль:** `crates/archie-stagingfs/` (`desktop_cleaner.rs`, `audit_logger.rs`).

**Контекст.** Голосовой ассистент с доступом к файловой системе и LLM-рецептами не может допускать необратимых операций: одна галлюцинация или неверный SOP — и пользователь теряет данные. Пользовательские страхи «ИИ удалит мне файлы» — прямой барьер доверия и принятия (и категория в Threat Model). Продуктовые сценарии («убери рабочий стол») при этом требуют массовых перемещений.

**Решение.** Необратимые операции запрещены как класс. Контроллер `archie-stagingfs` физически блокирует системный вызов Delete: любая «очистка» или SOP-шаг с удалением **перемещает** файлы в карантинную директорию `~/Archie_Staging` (например, `~/Archie_Staging/2026-05-15_cleanup/`), путь назначения фиксируется в `action_audit_log`. Восстановление — ручное перемещение пользователем из карантина; политика авто-очистки карантина не предусматривается (она была бы скрытым удалением). Из `SystemActionRequest/Response` прямое удаление отсутствует как категория — `action_category` ограничен `MEDIA_CONTROL | STAGING_MOVE | GIT_OPERATION | WORKSPACE_SWITCH | MCP_TOOL_CALL`.

**Последствия.** Позитив: инвариант «невозможно потерять данные из-за Archie» верифицируем и является продуктовым аргументом; трасса аудита покрывает каждое перемещение. Негатив: диск расходуется на карантин (нужна UX-подсказка пользователю); операция «настоящего удаления» недостижима через Archie — пользователь должен удалять средствами ОС; карантин требует места в `storage/` и, потенциально, квоты.

**Альтернативы.** Корзина ОС — отклонена: семантика и сроки автоочистки платформенно-различны и зависят от пользовательских настроек; «мягкие» флаги удаления на уровне SOP — отклонены: обходятся при компрометации, тогда как блок syscall'а в Rust-контроллере — жёсткая гарантия; требование подтверждения перед каждым удалением — отклонено: не спасает от ошибок подтверждения и ломает автономность Tier 1.

**Compliance-хуки:** тест физического запрета Delete (попытка удаления через любой путь API); аудит `action_audit_log` на 100% перемещений.

#### ADR-010: Экспоненциальное затухание индекса фрустрации с полураспадом, зависящим от миссии

**Статус:** Accepted. **Фаза 2.** **Модуль:** `proactivity/frustration_scorer.py`.

**Контекст.** Базовые эвристики (+10 `BROWSER_TAB_STALL_15M`, +15 `IDE_CODE_REWRITE_3X`, +20 `CONSOLE_EXCEPTION_4X`, +30 `AUDIO_HEAVY_SIGH_DETECTED`, порог 50) без затухания дают ложные срабатывания: разрозненные события многочасовой сессии суммарно превысят порог, даже если трудность давно снята. Зафиксирован и кейс пассивного контента: студент смотрит 15+ минут видеолекцию без скролла и вздыхает — линейный сумматор увидит «фрустрацию». При этом mission-state машина уже различает `STUDY_FOCUS / CODING_WORK / IDLE / GAMING_REST`.

**Решение.** Непрерывная модель: `S(t_k) = min(S_max, S(t_{k-1})·e^{−λ(M)·(t_k−t_{k-1})} + μ(M)·ψ(e_k,t_k)·ΔS(e_k))`, где S_max = 100, порог триггера 50, `λ(M) = ln 2 / T_1/2(M)`. Периоды полураспада по миссиям: **STUDY_FOCUS — 20 мин, CODING_WORK — 15 мин, IDLE — 5 мин, GAMING_REST — 1 мин**; множитель проактивности μ(M) = 1 в учёте/кодинге и 0 в GAMING_REST/IDLE (полная блокировка начислений при открытии Minecraft/Steam). Анти-ложноположительный фильтр `ψ`: при активном медиа-потоке в сфокусированном окне браузера (`active_media_playing`) таймер стагнации вкладки замораживается (ψ = 0), вес вздоха демпфируется (ψ = 0.5), чувствительность к ошибкам консоли и циклам переписывания сохраняется (ψ = 1.0). После вмешательства — сброс до 15.0 и рефрактерное окно 10 мин; при отмене Soft Widget — сброс до 10.0 и окно 20 мин.

**Последствия.** Позитив: сигнал отражает именно текущий когнитивный тупик, а не историю дня; верифицируемая математика (30-минутный сценарий кодинга в RFC-0001); телеметрия в `frustration_telemetry`. Негатив: параметры (полураспады, веса) — предмет калибровки по реальным сессиям; модель предполагает корректность детектора медиа-сессии (`media_session.rs`).

**Альтернативы.** Линейный сумматор с TTL-обнулением — отклонён: пороговые артефакты; скользящее окно фиксированной ширины — отклонено: не учитывает миссию (после переключения в игру фрустрация должна гаснуть за минуту); чисто LLM-классификация состояния — отклонена: недетерминированность и стоимость на каждый тик.

**Compliance-хуки:** симуляционный прогон `frustration_scorer.py` (0% срабатываний в GAMING_REST, заморозка при видео, триггер при >= 50).

#### ADR-011: Permission Tiers как принудительный контракт уровня ядра, а не соглашение на уровне промптов

**Статус:** Accepted. **Фаза 2.** **Модули:** `crates/archie-stagingfs/permission_tiers.rs`, `contracts/` (`PermissionTier` enum), SQL `action_audit_log`.

**Контекст.** Трёхуровневая модель разрешений описана в PAD как продуктовая семантика: **Tier 1** — автономные безопасные действия (управление музыкой, поиск), **Tier 2** — критические операции с карточкой Critical Approval (git push, отправка писем), **Tier 3** — оркестрация рабочих окружений (Context Workspaces) по явному запросу. Если бы эта семантика жила только в промптах LLM или настройках движка, компрометация промпта или баг рецепта обходила бы её. Threat Model требует enforcement независимо от поведения модели.

**Решение.** Уровни разрешений — **принудительный контракт (enforced kernel-level contract)**, сходящийся в Rust-ядре: `PermissionTier` — enum в `contracts/ipc_bridge.proto`; каждый `SystemActionRequest` несёт тир; исполнитель `archie-stagingfs` (и гейт песочницы SOP, ADR-005) валидирует тир **до** исполнения: Tier 2 без подтверждения `APPROVED_TIER2` не исполняется никогда, независимо от происхождения запроса (LLM, SOP-скрипт, ручной вызов). Каждое исполнение пишется в `action_audit_log` (тир, категория, `user_approval_status`: `AUTO_TIER1 | APPROVED_TIER2 | REJECTED_TIER2 | WORKSPACE_TIER3`, результат, пути). UI-часть: карточки `Tier2ApprovalCard` в `approval_modal` (resize-on-activation оверлея).

**Последствия.** Позитив: гарантия не зависит от LLM; полный аудит-трейл (SOC 2 evidence, разбор инцидентов); конформность B2B-требованиям. Негатив: каждое новое действие требует классификации в тир (иначе — дефолт в самый строгий); Tier 2-подтверждения добавляют фрикцию (осознанный компромисс в пользу безопасности).

**Альтернативы.** Согласие на уровне промпта — отклонено: нестойко к инъекциям; глобальный «параноидальный» тир для всего — отклонён: убивает ценность автономности; per-действие подтверждения через ОС (UAC-класс) — отклонён: UX и семантика вне контроля приложения.

**Compliance-хуки:** модульные тесты гейта тиров (отказ исполнения Tier 2 без подтверждения из любого источника); полнота записей `action_audit_log`.

#### ADR-012: Контракты и события в первую очередь — JSON Schema / proto codegen как единый источник истины для трёх языков

**Статус:** Accepted. **Фаза 1.** **Модуль:** `contracts/` (`events_envelope.schema.json`, `zsense_context.schema.json`, `blueprint_sop.schema.json`, `ipc_bridge.proto`).

**Контекст.** Три рантайма — TypeScript 5.8 (apps/desktop-ui), Rust (crates), Python 3.11+ (archie-engine) — обмениваются событиями шины (`EventEnvelope`), графами контекста Z-Sense и спецификациями SOP. Без единого источника истины типы пришлось бы дублировать руками в трёх местах, и любое расхождение (поле переименовано, enum добавлен) стало бы runtime-ошибкой на границе IPC — самом трудном для отладки месте распределённой системы.

**Решение.** Принцип «contracts-first»: структуры событий, payload'ы, enum'ы (`EventType`, `MissionState`, `PermissionTier`) и gRPC-сервисы определяются **только** в `contracts/` — Protobuf v3 для IPC (`ipc_bridge.proto`) и JSON Schema для конвертов событий/контекста/рецептов. Типы для TS/Rust/Python **генерируются** кодогенерацией (tonic, grpcio-стабы, JSON-Schema-кодгены) и коммитятся. Изменение контракта = PR в `contracts/` + регенерация + зелёные сборки всех трёх языков; изменения схемы событий шины без обновления контракта невозможны by construction. Числовые SLA остаются в RFC-0001; контракт фиксирует форму, RFC — бюджет.

**Последствия.** Позитив: одно определение — три согласованные реализации; дрейф типов ловится на compile-time; эволюция версионирована в одном месте; newcomers читают `contracts/` как карту системы. Негатив: шаг «изменил → регенерировал → пересобрал всё» замедляет быстрые итерации; сгенерированный код шумит в диффах (митигируется выделением в отдельные коммиты/директории).

**Альтернативы.** Ручное дублирование типов — отклонено (гарантированный дрейф); единый язык-«клей» с шарингом типов (напр. всё через TS) — несовместим с Rust/Python-разделением (ADR-008); REST+JSON без схем — отклонён по тем же причинам дрейфа и отсутствия стриминга.

**Compliance-хуки:** CI-гейт «контракт регенерирован и идентичен коммиту»; тесты валидации конвертов по JSON Schema на всех сторонах.

## ЧАСТЬ B. Глоссарий

### B.1. Правила использования

Одна запись — одно каноническое определение. Термины обязаны совпадать с кодовыми идентификаторами монорепо; документы комплекта используют написание из глоссария дословно. Новый термин входит через PR к этому файлу (чек-лист PR содержит пункт «термин добавлен в глоссарий»). Числа в определениях копируются только из RFC-0001. Синонимы допускаются как явные алиасы, но не как конкурирующие определения. Идентификаторы — английские, описательный текст — русский (двуязычная конвенция комплекта).

### B.2. Термины

**AEC3 (WebRTC Acoustic Echo Cancellation 3)** — алгоритм акустического эхоподавления из WebRTC, подключаемый через нативные биндинги livekit. Вычитает голос Archie из микрофонного входа по по-сэмплово синхронизированному референсному сигналу TTS, предотвращая самопрерывание при double-talk.

**ACL (Access Control List)** — список управления доступом, ограничивающий подключение к named pipe `\\.\pipe\archie-ipc-{session_id}` на Windows правами уровня пользователя. Вместе с `reject_remote_clients(true)` закрывает канал от чужих процессов.

**Archie («Архи»)** — автономный проактивный ИИ-напарник уровня ОС (OS-Level AI Symbiote): гибридный edge+cloud симбиот с полнодуплексным голосом, экранным зрением Z-Sense, трёхуровневой памятью и детерминированной моделью безопасности действий.

**Archie_Staging** — карантинная директория (`~/Archie_Staging`), в которую `archie-stagingfs` перемещает файлы вместо удаления; путь назначения фиксируется в `action_audit_log` (см. Staging FS, ADR-009).

**ASR / STT (Automatic Speech Recognition)** — потоковое распознавание речи через Sherpa-ONNX (Kroko ASR / Whisper) внутри единого аудио-цикла; вырабатывает частичные транскрипции для Turn Endpointing.

**Audit Log (`action_audit_log`)** — таблица SQLite с записью каждого действия системы: permission tier, категория, статус подтверждения пользователем, пути и результат исполнения. Основной evidence-артефакт безопасности и SOC 2.

**Barge-in** — перехват пользователем речи ассистента: трёхуровневый каскад (Silero VAD → Turn Endpointing → Turn Detection) вырабатывает `FORCE_STOP_AUDIO`; полная остановка TTS гарантируется быстрее чем за 200 мс.

**Blueprint / SOP (Smart Blueprint / Standard Operating Procedure)** — «Умный черновик»: правило автоматизации, сгенерированное облаком как черновик, утверждённое пользователем и скомпилированное в жёсткий детерминированный Python-скрипт, исполняемый песочницей при совпадении триггера >= 0.98.

**Cancel Countdown** — таймер обратного отсчёта (3–5 с) в `CancelCountdown.tsx` для немой отмены проактивного голосового вмешательства до произнесения стартовой фразы.

**Cloud Gateway** — `cloud_gateway.py`: асинхронные адаптеры облачных провайдеров (DeepSeek, OpenAI, Gemini) с маршрутизацией per-call и нормализацией ошибок для деградации (ADR-006).

**Context Workspace (Tier 3)** — оркестрация рабочих окружений по запросу («Я хочу учиться»): переключение окон/проектов/настроек через `workspace_orchestrator.rs`.

**Double-talk** — одновременная речь пользователя и ассистента; сценарий, в котором без корректного AEC3 фильтр эха отказывает и происходит ложное самопрерывание.

**Endpointing (Turn Endpointing)** — анализ пауз частичной транскрипции с порогами ~400 мс (внутрифразовые паузы) и ~1400 мс (завершение реплики) для определения конца высказывания пользователя.

**Event Bus (`archie-event-bus`)** — модульная асинхронная шина событий на Rust (tokio): маршрутизирует типизированные `EventEnvelope` между подсистемами за микросекунды, отслеживает `API_TIMEOUT`, доставляет `FORCE_STOP_AUDIO`.

**Event Envelope** — каноническая обёртка события шины (`event_id`, `timestamp_unix_us`, `event_type`, `publisher_module`, `mission_state`, `priority`, oneof-payload), определённая в `contracts/ipc_bridge.proto`.

**Graceful Degradation (изящная деградация)** — изящная деградация: офлайн — спроектированное UX-состояние; при `API_TIMEOUT` маршрутизация запросов переключается на локальную модель 1.5B с озвучиванием перехода (ADR-007).

**Frustration Index (Индекс Фрустрации, S(t))** — непрерывная величина в [0, 100], накапливаемая эвристиками (+10/+15/+20/+30) и затухающая экспоненциально с полураспадом 20/15/5/1 мин по миссии; порог вмешательства 50 (ADR-010).

**Full-Duplex Engine** — `full_duplex_engine.py`: единый внутрипроцессный полнодуплексный аудио-тракт (захват + AEC3 + VAD + STT + TTS) с общим аппаратным аудио-клоком (ADR-002).

**GGUF** — формат файлов квантованных весов LLM для llama.cpp; резервная модель хранится как `models/fallback_llm/qwen2.5_1_5b_q4_k_m.gguf` (квантование Q4_K_M, ~1080 МБ с контекстом 2048).

**Inner Monologue (Внутренний Монолог)** — скрытый запрос к облачной модели при `FRUSTRATION_SPIKE` («Юзер застрял… Что предложить?»), результат подготавливается в буфер TTS до истечения окна отмены виджета.

**IPC Bridge** — контракт межъязыкового взаимодействия `contracts/ipc_bridge.proto`: сервис `ArchieEventBusBridge` (StreamEvents, TriggerZSenseOcr, ExecuteSystemAction, ReportWorkerHealth) поверх gRPC/UDS/named pipes (ADR-003).

**Lazy Loading (LazyModelSlot, TTL)** — дисциплина памяти RFC-0001: ONNX-сессии создаются без арен (`enable_cpu_mem_arena = False`), тяжёлые модели подгружаются по событию и выгружаются по TTL (60/120/180 с), возвращая страницы ОС через `malloc_trim`.

**LanceDB** — встроенный (embedded) векторный индекс без серверного процесса; персистентность — файлы `storage/vector_store.lancedb/` поверх Arrow/mmap (ADR-004).

**mmap** — отображение файла в адресное пространство: векторный индекс и GGUF-веса читаются с диска по требованию страницами, не занимая RAM в простое (0 МБ для 1.5B в онлайне).

**MCP (Model Context Protocol) / MCP Hub** — открытый стандарт инструментов для LLM; `mcp_hub` (FastMCP, транспорты stdio / SSE / Streamable HTTP) — шлюз к Obsidian, Notion, Git, Jira/Slack; единственный выразительный канал SOP-рецептов (ADR-005).

**Mission State (`MissionState`)** — состояние машины миссий: `IDLE`, `STUDY_FOCUS`, `CODING_WORK`, `GAMING_REST`; определяет полураспад фрустрации, множитель проактивности и поведение виджета.

**Named Pipes** — транспорт IPC на Windows (`\\.\pipe\archie-ipc-{session_id}`) с ACL; асинхронный нативный примитив `tokio::net::windows::named_pipe` под gRPC/tonic.

**ONNX Runtime** — рантайм инференса ONNX-моделей на CPU (RapidOCR, NER, Silero VAD, Piper); конфигурируется последовательным режимом без арен памяти (Lazy Loading).

**Permission Tiers (Tier 1/2/3)** — трёхуровневая модель разрешений: Tier 1 — автономные действия (музыка, поиск); Tier 2 — критические с карточкой Critical Approval (git push, письма); Tier 3 — оркестрация окружений. Принудительный контракт, исполняемый Rust-ядром (ADR-011).

**Piper TTS** — локальный нейросетевой синтезатор (VITS на onnxruntime), потоково озвучивающий токены LLM, буферизованные до первого знака препинания.

**PII Data Sanitizer** — модуль анонимизации (`pii_sanitizer.py`): каскад регулярных выражений + квантованная ONNX NER-модель заменяют пароли, ключи API, карты и проприетарный код на `[REDACTED_API_KEY]` / `[REDACTED_FINANCIAL_DATA]` до любого облачного вызова.

**Proactivity Engine** — связка `mission_state_machine.py` + `frustration_scorer.py` + `inner_monologue.py`: детекция когнитивного тупика и инициация двухступенчатого вмешательства.

**RapidOCR (PP-OCRv5/v6)** — локальный OCR-движок (детекция+распознавание PaddleOCR-моделей на ONNX Runtime / OpenVINO без PaddlePaddle): ~80 МБ весов, инференс окна на CPU ~200 мс (185 мс эталон).

**Semantic Router** — `semantic_router.py`: перехватывает события до обращения к LLM, ищет ближайший триггер утверждённых рецептов в LanceDB и при совпадении >= 0.98 полностью блокирует облачный вызов, запуская SOP-скрипт.

**Shared Memory (archie_shm_vision, 16 МБ)** — фиксированный пул разделяемой памяти для zero-copy передачи кадров экрана 2560×1440 между `archie-os-hooks` и Python-воркером; по gRPC идут только `ShmFrameDescriptor` и индекс слота.

**Silero VAD** — вероятностный детектор голосовой активности (вес 1.8 МБ): < 1 мс на 30-мс чанк, задержка детекции 85–100 мс, точность > 95%; распознаёт шёпот и вздохи, игнорирует фоновые шумы.

**Single-Instance Lock** — именованный мьютекс в Rust (`single_instance.rs`), исключающий второй экземпляр приложения на Windows.

**SOP Sandbox (`sop_sandbox_runner`)** — изолированный исполнитель скомпилированных рецептов: AST-валидация whitelist'а MCP tool-call DSL + runtime-confinement + гейт Permission Tiers (ADR-005).

**Staging FS (`archie-stagingfs`)** — аппаратно-безопасный контроллер файловой системы: блокирует системный вызов Delete, перенося файлы в `Archie_Staging`, ведёт audit log (ADR-009).

**Tauri v2** — фреймворк desktop shell (Rust-ядро + системный WebView): инсталлятор ~8 МБ, двухоконная архитектура для обхода all-or-nothing семантики `set_ignore_cursor_events` (ADR-001).

**TCC** — (в контексте аудио-IPC) транзакционные схемы без блокировок; в Archie конфликтная целостность shm-слотов решается seqlock-версионированием (`seq_lock_version` в дескрипторе кадра).

**Tier 2 Approval Card (Critical Approval)** — модальная карточка подтверждения критических действий (`Tier2ApprovalCard.tsx`): «Я подготовил коммит. Пушим?»; показывается в расширенном (resize-on-activation) оверлее.

**Turn Detection** — семантический классификатор перехвата инициативы: отличает пассивные фоновые подтверждения («угу») от команд остановки («стоп, я понял»).

**UDS (Unix Domain Socket)** — локальный сокет `/tmp/archie-ipc-{uid}.sock` с правами 0600 на macOS/Linux — control-plane транспорт gRPC между Rust-ядром и Python-воркером.

**VAD (Voice Activity Detection)** — детекция голосовой активности; в Archie — Silero VAD (см.), первый уровень каскада Barge-in.

**VectorDB** — локальное векторное хранилище (LanceDB) для графа знаний Tier 3 и триггеров SOP; эмбеддинги — FastEmbed INT8 (~46 МБ, TTL 120 с).

**WAL (Write-Ahead Logging)** — режим SQLite в `archie_core.sqlite3`: запись телеметрии/аудита не блокирует чтение (конкурентный доступ памяти Tier 1 и роутера).

**XY-cut** — детерминированный геометрический алгоритм сортировки OCR-строк сверху вниз и слева направо (`xy_cut_sorter.py`) с фиксацией `scale_factor` и `origin`.

**Z-Sense** — событийное экранное зрение: захват по триггерам ОС (смена окна/вкладки, выделение текста, ошибки консоли), чтение через Accessibility API или RapidOCR, сборка сжатого JSON-графа после PII-санитизации; экономия 99% сетевого трафика.

**Z-Sense Graph (`ZSenseGraphResponse`)** — санитизированный JSON-слепок экранного контекста (активное окно, видимый текст, состояние ошибки, строки OCR с боксами и confidence), публикуемый событием `ZSENSE_GRAPH_READY`.
